# Задание 5 - Top + Алгоритмы планирования

Пятое задание марафона по системному программированию от PostgresPro.

Проект состоит из двух частей: терминальная утилита мониторинга процессов (аналог `top`) и симулятор алгоритмов планирования задач. Обе части реализованы на C, для реализации текстового интерфейса использовалась библиотека `ncurses`.

---

## Коротко по терминам

### Планировщик операционной системы

Планировщик - часть ядра ОС, которая решает какой процесс получит CPU в следующий момент времени. Решаемая им задача: процессов много, CPU один (или несколько), и каждый процесс хочет работать прямо сейчас.

Ключевые метрики качества планировщика:
- **Waiting time** - сколько процесс провёл в очереди, ожидая CPU
- **Turnaround time** - полное время от появления процесса до его завершения (`finish - arrival`)
- **Throughput** - сколько процессов завершается в единицу времени

### Вытесняющее и невытесняющее планирование

**Невытесняющее**: процесс получает CPU и работает до добровольного завершения или блокировки. Простое и предсказуемое. Недостаток - один долгий процесс заблокирует всех остальных.

**Вытесняющее**: планировщик может принудительно снять процесс с CPU по истечении кванта времени. Более справедливое. Недостаток - требует накладных расходов на переключение контекста.

### Реальные планировщики Linux

В Linux долгое время использовался **CFS** (Completely Fair Scheduler), который не делит время на кванты явно, а отслеживает «виртуальное время» каждого процесса и всегда выбирает того, кто получил меньше всего CPU. Позже его заменили **EEVDF** (Earliest Eligible Virtual Deadline First) - более математически строгая модель на основе дедлайнов. Оба алгоритма значительно сложнее тех, что реалзованы в данном проекте.

## Что сделано

### Часть 1 - мониторинг процессов (`аналог утилиты top`)

Терминальная утилита реализующая основной функционал `top`:

- отображение загрузки CPU и RAM с прогресс-барами
- таблица процессов отсортированная по CPU%
- шапка с uptime, load average, моделью CPU, детализацией us/sy/id/wa
- обновление в реальном времени (раз в секунду)
- обработка пользовательского вводы (выход по нажатию `q`)

### Часть 2 - симулятор различных алгоритмов планирования 

Реализованы три алгоритма на синтетическом наборе процессов:

- **FIFO** - невытесняющий, процессы выполняются в порядке прихода. Процесс выполняется до завершения.
- **Приоритетное планирование с очередями** - невытесняющее, процессы при поступлении добавляются в очередь готовых процессов, из которой выбирается процесс с наивысшим приоритетом (наименьшее значение `priority`). При одинаковом приоритете сохраняется порядок поступления. После запуска процесс выполняется до завершения.
- **Round Robin** - вытесняющий, каждый процесс получает определенный квант времени, затем уходит в конец очереди.


Для каждого алгоритма выводится диаграмма Ганта и таблица метрик.

## Как сделано

### Архитектура мониторинга

Проект построен на принципе `snapshot -> diff -> render`:

```
collectors -> system_snapshot_t -> engine -> computed_snapshot_t -> UI
```

**Collectors** читают `/proc` и заполняют структуры. На данном этапе никаких расчётов не производится - только парсинг. **Engine** сравнивает два последовательных снапшота и вычисляет метрики. **UI** отрисовывает результат.

**Важно!** один снапшот `/proc/stat` не даёт загрузку CPU, он содержит накопленные тики с момента загрузки системы. Процент загрузки считается как разница между двумя снапшотами:

```
CPU% = (busy_delta / total_delta) * 100 = (total_delta - idle_delta) / total_delta * 100
```

Аналогично для процессов: `utime + stime` из `/proc/[pid]/stat` - это тики с момента старта процесса, а не текущая загрузка.

### Источники данных

Вся информация о процессах находится в `/proc/[pid]/stat`. Он содержит около 50 полей в одной строке. Сложность парсинга в том, что поле имени процесса (`com`) обёрнуто в скобки и может содержать пробелы, что требует поиска первой и последней скобки и отдельного парсинга полей до и после.

## Раздел откровений

Самым неожиданным оказалось то, насколько `/proc` устроен по-разному для разных файлов - это настоящий зоопарк форматов. `/proc/meminfo` и `/proc/stat` - построчные форматы, а `/proc/[pid]/stat` - одна длинная строка. Ещё интереснее оказался вопрос единиц измерения: `rss` в `/proc/[pid]/stat` приходит в страницах памяти, а не в байтах (в первый раз напоролся и MEM% был сильно занижен).

Еще, интересная тема: у меня VSCode установлен через flatpak. Когда я запустил монитор в первый раз удивился, почему у меня так мало отображаемых процессов. Позже понял, что терминал в ide видит через `/proc` только процессы своего пространства имен, а не всей системы.

Работа над проектом заметно повысила понимание того, как планирование процессов устроено в Linux на практике. Читать про алгоритмы планирования в теории - одно, а написать собственный FIFO и Round Robin - совсем другое.
В планах расширить проект до уровня `htop`: добавить цвета через ncurses color pairs, интерактивную сортировку по любой колонке клавишами, возможность kill процесса прямо из интерфейса, и загрузку по ядрам процессора вместо общей агрегированной. На стороне симулятора интересно было бы добавить SJF и попробовать брать данные не из синтетического набора, а из реального снапшота системы.
