# Задание 7 - Симулятор многопоточного планировщика

Часть 2 седьмого задания марафона по системному программированию от PostgresPro.

## Что реализовано

Симулятор трёх алгоритмов планирования, где каждый процесс представлен отдельным потоком:

- **FIFO** - невытесняющий алгоритм, процессы выполняются в порядке поступления в очередь
- **Round Robin** - вытесняющий алгоритм с фиксированным квантом времени
- **Priority** - невытесняющий алгоритм, выбирается процесс с наименьшим значением `priority`

## Структура файлов

Я решил не трогать уже имеющиеся реализации алгоритмов для чистоты, поэтому создал отдельный симулятор в ветке **sched_mt**, используя смыслы уже работающих алгоритмов.

```
include/
    sched_mt/sched_mt.h         - API многопоточного планировщика

src/
    sched_mt/sched_mt.c         - реализация 
    main.c                      - тесты и демо
```

## Архитектура

```
main
 |--- поток-планировщик (один)
 |     1. выбирает из очереди 
 |     2. будит нужный процесс 
 |     3. передает ему процессор
 |     4. ждёт освобождения процессора
 |--- потоки-процессы (много)
       1. ожидают своего прибытия
       2. вдобавляются в очередь 
       3. ждут процессор 
       4. выполняются
```

## Реализация

Все алгоритмы планирования реализованы в одной структуре `scheduler_mt_t`. Общая логика работы потоков одинакова и описана выше. Отличие алгоритмов находится только в функции `queue_pop()`.

`queue_pop()` отвечает за выбор следующего процесса и для каждого алгоритма выбирает соответствующий. После выбора элемент удаляется из очереди сдвигом оставшихся элементов.

Для синхронизации используются два уровня:
- `queue_mutex` защищает общую очередь процессов;
- `proc->mutex` защищает состояние конкретного процесса.

Используются два условных сигнала (`condition переменные`):
- `queue_cond` - уведомление планировщика о появлении нового процесса в очереди;
- `cpu_cond` - уведомление планировщика об освобождении CPU.

## Раздел откровений

Вот здесь у меня есть что рассказать. Во-первых, для всех алгоритмов реализована одни публичные функции инициализации планировщика и добавления процесса - поэтому программисту необходимо самому следить за корректностью передаваемых в функцию аргументов (например, кванта времени для RR). 

Во-вторых, в первом варианте реализации я думал, что одной cond-переменной хватит: она использовалась и для ожидания появления процессов в очереди, и для уведомления планировщика об освобождении процессора. На первый взгляд это казалось логичным: есть очередь, есть событие изменения состояния - значит достаточно одного сигнала.
По факту при тестах я заметил, что процессы выполняются странно: в логах было видно, что следующий процесс начинал выполняться до того, как предыдущий успевал освободить отработать. Явно заметил проблему только после задания процессам разное время прибытия и они начали появляться во время выполнения другого процесса, что значило, что планировщик реагирует не на то событие и просыпался не только после завершения текущего процесса, но и когда новый процесс просто добавлялся в очередь. 
Много времени занял именно поиск причины.

Главный вывод после этой реализации - не натягивать сову на глобус. Понимая логику алгоритмов их реализация не создала проблем, труднее было правильно организовать взаимодействие потоков и сигналы потоку-планировщику.
