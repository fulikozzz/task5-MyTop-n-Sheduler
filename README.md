# Параллельная сортировка слиянием

## Что реализовано

Реализованы три варианта сортировки слиянием:

- **`merge_sort`** - обычная однопоточная
- **`parallel_merge_sort`** - параллельная сортировка, однопоточное слияние
- **`parallel_merge_sort_mt`** - параллельная сортировка, параллельное слияние через бинарный поиск медианы

## Структура файлов

```
include/
    sort/merge_sort.h         - API всех вариаций сортировок

src/
    sort_merge_sort.c         - реализация всех вариаций сортировок
    main.c                    - тесты и демо
```

## Реализация многопоточных вариаций

### Параллельная сортировка, однопоточное слияние

```
parallel_merge_sort(arr, left, right):
    spawn поток, сортирующий arr[left..mid]     - pthread_create
    сортируем arr[mid+1..right]                 - текущий поток
    sync                                        - pthread_join
    merge(arr, left, mid, right)                - однопоточное слияние
```

Два потока сортируют свои половины параллельно, затем результат сливается однопоточно.

### Параллельная сортировка, параллельное слияние через бинарный поиск

```
merge_mt(src, l1, r1, l2, r2, dst, l3):
    гарантируем n1 >= n2
    mid1 = середина большего массива
    mid2 = binary_search(src[mid1], src, l2, r2)
    mid3 = l3 + (mid1 - l1) + (mid2 - l2)
    dst[mid3] = src[mid1]                      - медиана на место
    spawn поток → merge_mt(левые части)        - pthread_create
    merge_mt(правые части)                     - текущий поток
    sync                                       - pthread_join
```

Медиана большего массива делит оба массива на части так, что левые части можно слить независимо от правых.

## Решения при исправлении ошибок и рефакторинге кода

1. При первых тестах на больших массивах программа постоянно падала с segfault. Оказалось, что без ограничения рекурсия создаёт поток на каждый вызов, каждый из которых занимает около 8 МБ стека. Стек переполнялся и программа падала. Было решено добавить ограничение в виде порога разбиения массива. Если разбиваемые части массива содержат менее 10к элементов - уходим в обычную однопоточную сортировку.
2. Аргументы передаются в поток через указатель. Так как если выделить их на стеке вызывающей функции, к тому моменту когда поток до них доберётся, функция может уже завершиться и стек будет недействителен. Память для хранения аргументов выделяется динамически и освобождаются самим потоком.
3. В случае ошибок создания потоков в целях стабильности программы было решено переходить на однопоточную сортировку.

## Результаты тестов

На массивах малых объемов однопоточная сортировка показыывает себя лучше многопоточных версий, так как отсутствуют накладные расходы на создание и синхронизацию потоков. При однопоточном слиянии средняя алгоритмическая сложность O(n). Параллельное слияние через бинарный поиск имеет несбалансированную рекурсию и в худшем случае один из рекурсивных вызовов обрабатывает 3/4 элементов, что даёт сложность слияния O(log^2(n)) + бинарный поиск на каждый уровень рекурсии (формулы алгоритмической сложности очень страшные в статье.
На массивах больших объемов многопоточные сортировки выигрывают кратно. В моем случае я получал превосходство многопоточных версий уже на массивах размерностью > 15к элементов.
